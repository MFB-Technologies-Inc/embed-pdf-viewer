# CU-C3 decisions

Decisions made while regenerating the vectors for upstream `cda9e82a4` and writing the work order
for CU-C4 to CU-C8.

## CU-C3-D1. The plugin generator's 9 type errors stay; the plugin vectors come from it as it is

Reversed on 2026-11-27 by the user's ruling: the three lines are a fix to port tooling, not an
upstream TS edit. CU-C4 made them and regenerated the plugin vectors twice (see
[`CU-C4.md`](CU-C4.md)). The record below is the decision as CU-C3 took it.

Decision: `tooling/plugin-conformance` is not edited in this job. `typecheck` still reports the 9
errors CU-C2 found, and the plugin vectors in `fc22e1e80` were generated by the unfixed generator.
Reason: the brief for this job says not to hand-edit TS to make checks pass, and an attempt to make
upstream's own fixture change in the generator was refused in this session. The fix is three
lines, each one upstream made in `packages/plugin/form/test/*.test.ts` (`29232ea27`, `b45d916cb`):
`forAnyone: false` in `base()` of `tooling/plugin-conformance/src/suites/form-current-fixtures.ts`,
`hasImage: false` in its `pushbutton()`, and `setButtonImage: true` in the `forms` table of
`tooling/plugin-conformance/src/fake-engine.ts` (the table the error at
`tooling/plugin-conformance/src/fake-engine.ts:183` names), after `setSignatureAppearance`. The
generator runs under `tsx`, which doesn't type-check, so both regenerations finished and matched.
Cost: `typecheck` stays red until someone makes the change. When it lands, the vectors whose
fixtures come from `form-current-fixtures.ts` (`acrojs`, `actions`, `form-core-lifecycle`,
`form-core`, `form-groups`, `signature-plugin`, `stamp-api` suites) gain `forAnyone: false` on
fixture rows and must be regenerated once more. The Rust replays are unaffected either way: a row
the fixture gives is a row the replay echoes.
Reverse: the controller rules the change is a generator fix (as 2026-11-27 CU-C3 `3a587e088`
was), it is made, and `regen2x.sh` runs again.

## CU-C3-D2. CU-C4 reads all three new row members, `layout` and `hasImage` included

Decision: the read of `forAnyone` (field rows), `hasImage` (push button rows) and `layout` (widget
rows and widget annotation rows) all go to CU-C4. CU-C5 keeps every write of `layout` and the
image, the change op and the analysis rule.
Reason: of the 16 failing `epdf-engine` tests, 7 fail on two or three of the members in the same
case, and 2 more (`annotation_reader`, `a_widget_update_renames`) on `layout` alone (`results/CU-C3-cargo-failures.md`). Split by PR, CU-C4 could not meet its own done line
("anyone-fields, attribution, prediction, transfer and signature-mark vectors pass"). The reads
are small: `/MK /TP` and `EPDFAnnot_HasMKIcon`, both already wrapped in `pdfium`
(`crates/pdfium/src/stamp.rs:409-430`).
Cost: about an hour moves from CU-C5 to CU-C4, and the two jobs share `readFormSnapshot` and the
widget row code.
Reverse: CU-C5 takes the `layout` and `hasImage` reads back, and CU-C4's done line excludes them.

## CU-C3-D3. The mark's move to the shared drawing is CU-C5's

Decision: `7d5691a5a` (#1165) draws a signature mark through `drawingFor` and the document's
drawing index, which stores a picture once; CU-C5 ports it with the push button's image. CU-C4
ports `445e34a69` (#1162), which stops recording the mark's fit on the widget.
Reason: the plan gives "a picture shown in many fields, signature marks included, is stored once"
to CU-C5, and `DrawingIndex` (`crates/epdf-engine/src/features/annotation/write/stamp.rs:32`) is
the code both share.
Cost: after CU-C4, `changes/signature-mark.json` case `a-png-a-jpeg-and-a-pdf-fill-a-signature-field`
and `changes/widget-rotation.json` case `a-turn-turns-the-mark-and-undo-puts-it-back` still differ
on object numbers (78 and 79 expected where Rust writes 80 and 81; 84 and 85 for 86 and 87), so
CU-C4's signature-mark line is met except those two. This is inferred from the vector diff and
the commit that added `drawingFor`; no Rust ran it.
Reverse: CU-C4 takes the mark half of `7d5691a5a`.

## CU-C3-D5. D-1 leaves nothing to deprecate in Swift, Kotlin or .NET

Decision: CU-C7 and CU-C8 add no deprecation attribute for D-1. The Rust core keeps
`filled_by`, `filled_by_name` and `filled_at` and returns `None` (CU-C4).
Reason: no wrapper types those members. `git grep -i filledBy -- platforms` finds nothing; the
plugin's `FormField` record carries them only inside `fields_json`, "the engine's field record,
whole, as JSON" (`crates/plugins/form/src/ffi.rs:294-296`). `import_values` takes no attribution
option (`crates/plugins/form/src/ffi.rs:1569`, which passes `None`). D-1's wrapper half, as
written, has no target.
Cost: none in code. A wrapper user who parsed `filledBy` out of `fields_json` gets `null` with no
compiler warning; the release notes should say so.
Reverse: type the three members on `FormField` and deprecate them, which adds API only to mark it
dead.
