The five `com.embedpdf` Maven artifacts (`embedpdf-bindings`, `embedpdf`, `embedpdf-javascript`, `embedpdf-models` and `embedpdf-compose`), caught up with upstream `embedpdf/embed-pdf-viewer` `cda9e82a4` (still viewer 3.4.0). Everything in `docs/releases/0.0.0-android.3.md` still applies except as below.

Gradle: `implementation("com.embedpdf:embedpdf-compose:0.0.0-android.4")`

The engine is `embedpdf-bindings` at `0.0.0-engine.1a68bff677299ac0`, up from `0.0.0-engine.64cf9e896bdd28bc` ([`513fcb0ce`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/513fcb0ce)), still linked with the runtime fork's slices at `9472117ed`. The release carries `embedpdf-android-maven-0.0.0-android.4.zip` and its `.sha256`, and the artifacts go to the GitHub Packages Maven registry as before.

## Breaking changes from 0.0.0-android.3

The generated form records grow members, so positional construction breaks: `FormField` (`forAnyone`), `FormWidgetRecord` (`layout`), `FormCreateFieldInput` (`forAnyone`, `layout`), `FormWidgetPlacement` (`layout`) and `FormFieldPatch` (`forAnyone`). `FormFieldDetail.Pushbutton` now carries `hasImage` ([`e52137ce0`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/e52137ce0), [`81e940680`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/81e940680)).

`filledBy`, `filledByName` and `filledAt` in `FormField.fieldsJson` now always read `null` (upstream #1162). The engine no longer writes who filled a field into the PDF, and it ignores what an older file holds. No Kotlin property ever typed them, so nothing stops compiling; code that parsed them out of the JSON gets `null`.

## Added

Fields anyone fills in (upstream #1163, [`db41381cb`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/db41381cb)). `FormField.forAnyone` reads it, and `FormCreateFieldInput` and `FormFieldPatch` set it. Any signer may fill such a field, whatever its group, and a signing that names no lock locks every anyone field that holds a value. A field in a group, or a signature field, can't be for anyone: `invalid-input`.

Push buttons that hold a picture (upstream #1165, [`8ed1f4f77`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/8ed1f4f77)). `FormCapability.setButtonImage(field, image)` puts a PNG, a JPEG or a one-page PDF in every widget of a push button, fitted whole inside each widget's border, and `null` takes it out. It returns a `FormFieldUpdateResult`. `hasImage` on the push button detail says whether a button holds one. A widget's `FormWidgetLayout` (caption, image, caption below, above, right or left, or caption over the picture) says how caption and picture sit, read from `FormWidgetRecord.layout` and set on create, placement and `updateWidget`. The PDF stores a picture once however many buttons show it, sharing the store signature marks and stamps use.

`setButtonImage` goes straight to the engine as one change, outside the history's undo, so an undo after it steps back over the change before it, not the picture ([`064026d17`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/064026d17)). It throws `permission-denied` for a field a signature locked or the session may not fill ([`1c42006dc`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/1c42006dc)).

## Fixed

Filling a field or drawing a mark keeps earlier signatures valid (upstream #1162, [`fee9339ec`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/fee9339ec)). A fill wrote who filled the field into its `/EMBD_Metadata`, and a mark recorded its fit on the widget; a strict reader took either change, to an object an earlier signature covers, as a modification after signing. Neither is written now.

A new appearance on a signature field nobody signed no longer marks an earlier signature as broken (upstream #1161, [`dad7474af`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/dad7474af)).
