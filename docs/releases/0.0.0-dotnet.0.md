The first release of the C# viewer packages: `EmbedPDF.Runtime`, `EmbedPDF`, `EmbedPDF.Models`, `EmbedPDF.Extensions.DependencyInjection` and `EmbedPDF.Scripting.Jint`. They're on the GitHub Packages NuGet feed of `MFB-Technologies-Inc`, not on nuget.org, and this prerelease carries the same five `.nupkg` files with their `.sha256` checksums and `package-manifest.runtime.json`, the runtime's per-RID validation record. The port is the .NET parity work ([`94822b7a9`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/94822b7a9)), built with the .NET 11 SDK and tested on .NET 10 and 11 since [PR #40](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/pull/40) ([`4796c479c`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/4796c479c)).

```xml
<PackageReference Include="EmbedPDF" Version="0.0.0-dotnet.0" />
```

These packages are separate from `EmbedPDF.Engine`, the narrow headless reader released as `dotnet-engine-0.0.0-local-<sha12>`. Neither depends on the other, and each bundles its own PDFium, so an app that loads both pays for two copies. Pick one: the engine for a server that only reads, the viewer for an app that shows and edits documents.

## The packages

| Package | Version | What it is | Depends on |
|---|---|---|---|
| `EmbedPDF.Runtime` | `0.0.0-engine.<hash>` | The native `epdf-viewer-host` library and the PDFium it links, under `runtimes/<rid>/native/`. No managed code. | nothing |
| `EmbedPDF` | `0.0.0-dotnet.0` | The facade: `PdfViewer`, the 23 plugin capabilities, `PixelBuffer` and the platform service interfaces. Assembly `EmbedPDF.Viewer.dll`, namespace `EmbedPDF`. | `EmbedPDF.Runtime` at the pinned version, `Microsoft.Extensions.Logging.Abstractions` 10.0.0 |
| `EmbedPDF.Models` | `0.0.0-dotnet.0` | UI-neutral `INotifyPropertyChanged` models: `PdfReaderModel`, `StageReaderModel`, `SearchModel`, `ThumbnailModel`, `TiledPageModel` and the rest. | exactly `[0.0.0-dotnet.0]` of `EmbedPDF` |
| `EmbedPDF.Extensions.DependencyInjection` | `0.0.0-dotnet.0` | `services.AddEmbedPdf(...)`, which registers one `PdfViewer`. | `EmbedPDF`, `Microsoft.Extensions.DependencyInjection.Abstractions` 10.0.0 |
| `EmbedPDF.Scripting.Jint` | `0.0.0-dotnet.0` | `JintScriptEngineFactory`, the engine for document JavaScript, with time, memory and stack limits and no access to .NET types. | `EmbedPDF`, Jint 4.18.0 |

`EmbedPDF.Runtime` is versioned by a hash of every input of the native library (`platforms/dotnet/dotnet-engine-hash.sh`), not by the release, so a later release that changes no Rust reuses it. The exact version is the one `platforms/dotnet/EmbedPDF.Runtime/EmbedPDF.Runtime.props` pins at this tag, and it's in the asset names. `EmbedPDF.Models` takes exactly one `EmbedPDF` version because it calls the facade's internals through `InternalsVisibleTo`; `packaging/libraries.py` refuses to pack it with any other range.

The four managed packages target `net10.0` only and set `IsAotCompatible`. A .NET 11 app loads the same assemblies, so .NET 10 and .NET 11 are both supported from one build, and the `Microsoft.Extensions.*` references stay on 10.x so a .NET 10 app never pulls a newer major. The facade's assembly is `EmbedPDF.Viewer.dll` rather than `EmbedPDF.dll`, which would collide with win-x64 PDFium's `embedpdf.dll` on a case-insensitive file system.

One `EmbedPDF.Runtime` package covers five RIDs: `linux-x64`, `linux-arm64`, `osx-arm64`, `osx-x64` and `win-x64`. There's no per-RID package as there is for `EmbedPDF.Engine`. A RID-specific build copies that RID's host and PDFium beside the app; a portable build keeps them under `runtimes/<rid>/native/`, and the resolver looks in both. The Linux host carries a `$ORIGIN` runpath and the macOS host an `@loader_path` one, so no `LD_LIBRARY_PATH` or `DYLD_LIBRARY_PATH` is needed. A RID with no host fails with `NativeRuntimeNotFoundException`, which names the RID and every path it tried.

## Adding the feed

GitHub Packages asks for a token even to read. Use a personal access token with `read:packages`, kept out of source control (here in the `EMBEDPDF_FEED_TOKEN` environment variable), and map the `EmbedPDF` ids to the feed so they never resolve from nuget.org:

```xml
<!-- nuget.config -->
<configuration>
  <packageSources>
    <add key="nuget.org" value="https://api.nuget.org/v3/index.json" />
    <add key="embedpdf" value="https://nuget.pkg.github.com/MFB-Technologies-Inc/index.json" />
  </packageSources>
  <packageSourceMapping>
    <packageSource key="embedpdf"><package pattern="EmbedPDF" /><package pattern="EmbedPDF.*" /></packageSource>
    <packageSource key="nuget.org"><package pattern="*" /></packageSource>
  </packageSourceMapping>
  <packageSourceCredentials>
    <embedpdf>
      <add key="Username" value="<your GitHub user>" />
      <add key="ClearTextPassword" value="%EMBEDPDF_FEED_TOKEN%" />
    </embedpdf>
  </packageSourceCredentials>
</configuration>
```

`EmbedPDF` brings `EmbedPDF.Runtime` with it. Add the others at the same version when you use them:

```xml
<PackageReference Include="EmbedPDF" Version="0.0.0-dotnet.0" />
<PackageReference Include="EmbedPDF.Models" Version="0.0.0-dotnet.0" />
<PackageReference Include="EmbedPDF.Extensions.DependencyInjection" Version="0.0.0-dotnet.0" />
<PackageReference Include="EmbedPDF.Scripting.Jint" Version="0.0.0-dotnet.0" />
```

## Using it

A viewer installs only the plugins you set on `PdfViewerOptions` (or `PdfViewerOptionsBuilder`). Each plugin is reached through a `Get{Plugin}Async` accessor that returns an `IDisposable` capability, taking the document when the plugin is per document. An accessor for a plugin you left out throws `PdfException` with `PdfErrorCode.Unsupported`.

```csharp
using EmbedPDF;

await using var viewer = await PdfViewer.CreateAsync(new PdfViewerOptions { Search = new(), Render = new() });
var document = await viewer.OpenFileAsync("report.pdf");

using var search = await viewer.GetSearchAsync(document);
var result = await search.SearchAsync(new SearchQuery("the"));

using var render = await viewer.GetRenderAsync(document);
var page = (await viewer.GetPagesAsync(document))[0].Page;
var rendered = await render.RenderPageAsync(page, new RenderPageOptions { Scale = 1 });
// rendered.Image is a PixelBuffer: copy it into your framework's bitmap.
```

Every call is a `Task`-returning `...Async` method that throws `PdfException` and takes a `CancellationToken` last. Event streams are `IAsyncEnumerable<T>`. Documents also open from a `Stream`, a `ReadOnlyMemory<byte>` or a `Uri`.

With a service container, `AddEmbedPdf` registers the viewer, which isn't started yet: call `StartAsync()` once before using it. Document JavaScript runs only with a script engine, which `EmbedPDF.Scripting.Jint` supplies:

```csharp
using EmbedPDF;
using EmbedPDF.Scripting.Jint;
using Microsoft.Extensions.DependencyInjection;

var services = new ServiceCollection()
    .AddEmbedPdf(options => options
        .Search(new SearchConfig())
        .Render(new RenderConfig())
        .Actions(new ActionsConfig { JavaScript = new ActionsJavaScriptConfig(true) { Engine = new JintScriptEngineFactory() } }))
    .BuildServiceProvider();
var viewer = services.GetRequiredService<PdfViewer>();
await viewer.StartAsync();
```

`EmbedPDF.Models` is what a view binds to. `new PdfReaderModel(ReaderFeatures.Search | ReaderFeatures.Links)` opens a document and, once its `Phase` is `ReaderPhase.Ready`, hands you a session with a `StageReaderModel` and a `SearchModel`. A model raises `PropertyChanged` on the `SynchronizationContext` it was made on, so make models on the UI thread. `platforms/dotnet/README.md` has the full plugin table with the platform services each one needs, the threading and disposal rules, and the `StageReaderModel` contract a page view implements. `platforms/dotnet/samples/EmbedPDF.Sample.Console` uses all four managed packages the way an outside app does.

`scripts/check-api-coverage.py --platform csharp` maps the facade to the Rust plugins' exports: 880 members, 739 ported, 0 pending and 141 exclusions, each with its reason in `platforms/dotnet/csharp-api-coverage.json`.

## Validation

The release train built and checked the packages in `.github/workflows/release-dotnet.yml`, and `dotnet-viewer-release` runs only when every job there passed. Every job that runs .NET installed SDK 11.0.100 and the .NET 10.0.15 runtime, each archive checked against Microsoft's published SHA-512 before it was unpacked (`.github/actions/setup-dotnet`).

Each RID's viewer host was built on its own native runner, never under emulation: `linux-arm64` and `linux-x64` in a `debian:trixie` container pinned by digest on `ubuntu-24.04-arm` and `ubuntu-24.04`, `osx-arm64` on `macos-15`, `osx-x64` on `macos-15-intel` and `win-x64` on `windows-2022`. Each was stripped and staged with its checksum-checked PDFium. `runtime-pack`, on `linux-arm64` in the same container, then checked that `EmbedPDF.Runtime.props` pins the tree's engine hash, packed the five slices into one `EmbedPDF.Runtime` (re-checking every staged file), generated the bindings, ran `EmbedPDF.Viewer.Tests` and `EmbedPDF.Models.Tests` on both `net10.0` and `net11.0`, ran the C# API coverage check, and packed the other four packages at `0.0.0-dotnet.0`.

Every RID's packages then went through `package.py validate-runtime` on that RID's native host. It restores `EmbedPDF` and `EmbedPDF.Runtime` from a local feed into a fresh consumer with its own NuGet cache and source mapping, builds a `net10.0` app and a `net11.0` app, each RID-specific and portable, with `EPDF_NATIVE_DIR`, `PDF_RUNTIME_LIB_DIR`, `LD_LIBRARY_PATH`, `DYLD_LIBRARY_PATH` and `DYLD_FALLBACK_LIBRARY_PATH` unset, and reads `report.pdf`'s 14 pages. With the host hidden each build must fail with `NativeRuntimeNotFoundException`, and with PDFium hidden the RID-specific build must fail to load. Only then is the RID `VALIDATED` in `package-manifest.runtime.json`.

The `consumer` job ran `platforms/dotnet/dotnet-consumer.sh` on `linux-arm64`, `linux-x64`, `osx-arm64` and `win-x64`: the console sample, built from all five packages in a local feed, opens, searches, renders a page to PNG, adds a square annotation, saves and reopens, drives `SearchModel` and runs one script in Jint. On the two Linux RIDs it also ran as a NativeAOT binary.

Before pushing anything, `platforms/dotnet/packaging/release-viewer.sh` checked that there is exactly one `EmbedPDF.Runtime.0.0.0-engine.<hash>` and the four others at `0.0.0-dotnet.0`, that `EmbedPDF` depends on that runtime and `EmbedPDF.Models` on exactly `[0.0.0-dotnet.0]`, that every nuspec names this repository, and that no draft, partial release or bare tag `0.0.0-dotnet.0` is in the way. It pushed `EmbedPDF.Runtime` first, so the feed never held a package whose dependency was missing.

The three signature route tests (`SignatureTransportTests`) were skipped, since the train doesn't set `EMBEDPDF_SIGNATURE_ROUTES` or build their helper. The run's logs have the test counts.

## Known gaps

There's no UI package, by design (D6 in `docs/superpowers/plans/2026-11-20-dotnet-parity.md`). .NET has no single cross-platform first-party UI framework to target, so `EmbedPDF.Models` is the parity line, and each app writes its own page view, tiling and gesture handling on top of `StageReaderModel` and `TiledPageModel`. Swift's `EmbedPDFUI` is one complete implementation of that contract (`platforms/apple/EmbedPDF/Sources/EmbedPDFUI/`).

The viewer and model test suites ran on `linux-arm64` only. The other RIDs were checked by the consumer smoke test and, except `osx-x64`, the console sample. NativeAOT was checked on `linux-x64` and `linux-arm64` only: the sample ran framework-dependent on `osx-arm64` and `win-x64`, and not at all on `osx-x64`. The Linux hosts were built and validated against `debian:trixie`'s glibc, which is the tested version, not a declared minimum. No `win-arm64` or `linux-musl-*` host is built.

A NativeAOT publish that includes `EmbedPDF.Scripting.Jint` reports six trim and AOT warnings (IL2104, IL3053 and four IL2026), all from Jint's CLR interop and JSON paths, which the package never enables. An app that needs no document JavaScript leaves the package out and publishes with none.

The public API isn't frozen yet. Every member is still in `PublicAPI.Unshipped.txt`, and package validation against a baseline (`EnablePackageValidation`, D8) starts with a later release, so `0.0.0-dotnet.1` may change any of it without a deprecation step.

Whether `EmbedPDF.Engine` stays a separate package is open: D2 is revisited now that the viewer has shipped.
