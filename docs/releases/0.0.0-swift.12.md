The `EmbedPDF`, `EmbedPDFModels` and `EmbedPDFUI` libraries, caught up with upstream `embedpdf/embed-pdf-viewer` `cda9e82a4` (still viewer 3.4.0). This tag is the commit the release train makes to pin the repository-root `Package.swift` and `platforms/apple/EmbedPDF/Package.swift` to `apple-engine-44a23eb0573339c7`, the engine it builds in the same run, replacing `apple-engine-ca2421677d81b1d9`, which 0.0.0-swift.11 pinned. No local package path or engine environment flag is required.

SwiftPM: `.package(url: "https://github.com/MFB-Technologies-Inc/embed-pdf-viewer", exact: "0.0.0-swift.12")`

The runtime fork is still `9472117ed` and Rust is still 1.100.0. The new engine comes from the Rust changes below.

## Breaking changes from 0.0.0-swift.11

The generated form records grow members: `FormField` (`forAnyone`), `FormWidgetRecord` (`layout`), `FormCreateFieldInput` (`forAnyone`, `layout`), `FormWidgetPlacement` (`layout`) and `FormFieldPatch` (`forAnyone`). Code that builds these values, usually test fixtures, needs the new arguments. `FormFieldDetail.pushbutton` now carries `hasImage`, so a `case .pushbutton` pattern has to bind it or use `case .pushbutton(_)`.

`filledBy`, `filledByName` and `filledAt` in `FormField.fieldsJson` now always read `null` (upstream #1162). The engine no longer writes who filled a field into the PDF, and it ignores what an older file holds. No Swift property ever typed them, so nothing stops compiling; code that parsed them out of the JSON gets `null`.

## Added

Fields anyone fills in (upstream #1163, [`db41381cb`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/db41381cb), Swift in [`663cccac6`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/663cccac6)). `FormField.forAnyone` reads it, and `FormCreateFieldInput` and `FormFieldPatch` set it. Any signer may fill such a field, whatever its group, and a signing that names no lock locks every anyone field that holds a value. A field in a group, or a signature field, can't be for anyone: `invalid-input`.

Push buttons that hold a picture (upstream #1165, [`8ed1f4f77`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/8ed1f4f77)). `FormCapability.setButtonImage(_:image:)` puts a PNG, a JPEG or a one-page PDF in every widget of a push button, fitted whole inside each widget's border, and `nil` takes it out. It answers a `FormFieldUpdateResult`. `FormFieldDetail.pushbutton(hasImage:)` says whether a button holds one. A widget's `FormWidgetLayout` (`caption`, `image`, `captionBelow`, `captionAbove`, `captionRight`, `captionLeft` or `captionOver`) says how caption and picture sit, read from `FormWidgetRecord.layout` and set on create, placement and `updateWidget`. The PDF stores a picture once however many buttons show it, sharing the store signature marks and stamps use.

`setButtonImage(_:image:)` goes straight to the engine as one change, outside the history's undo, so an undo after it steps back over the change before it, not the picture ([`064026d17`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/064026d17)). It throws `permission-denied` for a field a signature locked or the session may not fill ([`1c42006dc`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/1c42006dc)).

## Fixed

Filling a field or drawing a mark keeps earlier signatures valid (upstream #1162, [`fee9339ec`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/fee9339ec)). A fill wrote who filled the field into its `/EMBD_Metadata`, and a mark recorded its fit on the widget; A strict reader took either change, to an object an earlier signature covers, as a modification after signing. Neither is written now.

A new appearance on a signature field nobody signed no longer marks an earlier signature as broken (upstream #1161, [`dad7474af`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/dad7474af)). The change analysis now has a rule for a field, unsigned before and after, whose field and widgets change their `/AP` alone.

## Validation

## Known gaps

As in 0.0.0-swift.11. A `setButtonImage(_:image:)` call can't be undone through `HistoryCapability`.
