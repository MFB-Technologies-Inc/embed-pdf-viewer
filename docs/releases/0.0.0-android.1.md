The first Android release: five Maven artifacts under the group `com.embedpdf`, namely `embedpdf-bindings`, `embedpdf`, `embedpdf-javascript`, `embedpdf-models` and `embedpdf-compose`. They need `minSdk` 24 and `compileSdk` 36, and carry the engine for `arm64-v8a` and `x86_64`. The engine is `epdf-viewer-host`, the full Rust viewer host with every plugin, built with Rust 1.100.0 against NDK r29 and linked with the PDFium fork's `android-arm64` and `android-x64` slices at runtime fork `af480d0ce`. It is `embedpdf-bindings` at `0.0.0-engine.9d9ec62d682771fa`; the other four artifacts are at `0.0.0-android.1` and their POMs pick the engine, so an app never names that version. The package came in with [`54006ea89`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/54006ea89) (the facade, models and Compose views) and [`17bd82627`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/17bd82627) (the release zip, device checks and search highlights).

Gradle: `implementation("com.embedpdf:embedpdf-compose:0.0.0-android.1")`

## Getting it

The release carries `embedpdf-android-maven-0.0.0-android.1.zip` and its `.sha256`. The zip's root is a Maven repository holding all five artifacts, with a `maven-metadata.xml` per artifact and the checksum files a remote repository serves, so a build reads it with no token. Unzip it into the app's tree and name the directory in `settings.gradle.kts`:

```bash
V=0.0.0-android.1
base=https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/releases/download/$V
curl -fLO "$base/embedpdf-android-maven-$V.zip" -fLO "$base/embedpdf-android-maven-$V.zip.sha256"
sha256sum -c "embedpdf-android-maven-$V.zip.sha256"   # shasum -a 256 -c on macOS
unzip -q "embedpdf-android-maven-$V.zip" -d third_party/embedpdf-maven
```

```kotlin
dependencyResolutionManagement {
    repositories {
        google()
        mavenCentral()
        maven {
            url = uri(settingsDir.resolve("third_party/embedpdf-maven"))
            content { includeGroup("com.embedpdf") }
        }
    }
}
```

The cost is size: the zip holds both ABIs' engine and its native debug symbols (about 90 MB in the dry run `platforms/android/README.md` records), and the app's repository has to keep it, in Git LFS or downloaded in CI before the build.

This release also goes to the GitHub Packages Maven registry of `MFB-Technologies-Inc/embed-pdf-viewer`. GitHub Packages wants a token even to read a public package: every machine and CI job that resolves the artifacts needs a classic personal access token with `read:packages`, or the job's `GITHUB_TOKEN` when the build runs in a workflow of this repository. Keep `gpr.user` and `gpr.key` in `~/.gradle/gradle.properties`, not in the project:

```kotlin
maven {
    url = uri("https://maven.pkg.github.com/MFB-Technologies-Inc/embed-pdf-viewer")
    content { includeGroup("com.embedpdf") }
    credentials {
        username = providers.gradleProperty("gpr.user").orNull ?: System.getenv("GITHUB_ACTOR")
        password = providers.gradleProperty("gpr.key").orNull ?: System.getenv("GITHUB_TOKEN")
    }
}
```

The dependencies are the same from either source. Pick one artifact by what the app draws with, and add `embedpdf-javascript` only for PDF JavaScript:

```kotlin
dependencies {
    implementation("com.embedpdf:embedpdf-compose:0.0.0-android.1")    // or embedpdf-models, or embedpdf
    implementation("com.embedpdf:embedpdf-javascript:0.0.0-android.1") // optional
}
```

`embedpdf-compose` brings `embedpdf-models`, which brings `embedpdf`, which brings `embedpdf-bindings`. `embedpdf-models` has no Compose dependency. `embedpdf-compose` builds against Compose BOM 2026.06.01; a BOM from 2026.08.00 on resolves Compose 1.12, needs `compileSdk` 37, and hasn't been tried. `platforms/android/README.md` has the requirements table, R8, manifest and APK-size notes, and how to symbolicate a native crash from the `native-debug-symbols` classifier of `embedpdf-bindings`.

## The API

`PdfViewer(config, documentFetcher)` in `embedpdf` is the engine. `ViewerConfig` (or `ViewerConfigBuilder`) names the plugins, `start()` starts it, `open` takes bytes, a `URL` or a `Uri`, and `destroy()` ends it. Each plugin is a capability reached from the viewer, such as `viewer.search(document)` or `viewer.render(document)`, and an accessor for a plugin the config left out throws `PdfException` with `PdfException.Code.UNSUPPORTED`. `HttpDocumentFetcher` is the default fetcher; `ContentResolverDocumentFetcher` reads `content:` Uris. The plugin table in `platforms/android/README.md` maps each plugin to its capability and its `ViewerConfig` setting.

`embedpdf-models` holds one class per Swift model in `EmbedPDFModels` (`SearchModel`, `StageReaderModel`, `TextSelectionModel`, `HistoryModel` and the rest), each exposing `StateFlow`s. A model never makes a `CoroutineScope`: the caller runs its `suspend fun run()` in a scope it picks. `PdfReaderModel` is the whole reader, and `PdfViewerViewModel` holds one `PdfViewer` across configuration changes. `embedpdf-compose` draws them: `PdfReader` over a `PdfReaderModel` is a reader with a password prompt, search bar, panels, tool picker and history controls, and its pieces (`StageReader`, `SearchBar`, `ThumbnailStrip`, `SearchHighlightOverlay` and others) are public too.

PDF JavaScript runs in `androidx.javascriptengine` 1.1.1 through `JavaScriptSandboxEngineFactory` in `embedpdf-javascript`, passed to `ActionsJavaScriptConfig`. Signing uses `AndroidKeyStoreSigner`, `TrustAnchors` and `HttpSignatureTransport`. Annotations and form fields can be duplicated, and `AnnotationCapability` answers `isMovable`, `stageRemeasure` and `whenRemeasurable` ([`96d925b73`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/96d925b73)).

Two behaviors differ from Swift's `EmbedPDF`. A cancelled Kotlin caller never gets a value: the facade waits for the kernel and then throws the caller's `CancellationException`, even when the work finished, so an edit or save that had started still lands and the state needs reading again. `RedactionCapability.markMatches` is the one exception, returning what the kernel resolved ([`96d925b73`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/96d925b73)). And `PdfViewerViewModel.startedViewer()` on a cleared view model always throws `instance-closed` ([`f2b229179`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/f2b229179)).

The supported surface is `com.embedpdf.*`, checked by the API dumps in `embedpdf/api`, `javascript/api`, `models/api` and `compose/api`. The generated `uniffi.*` types are visible through the facade's typealiases but are not supported API, and a Rust change can rename one without notice. `platforms/android/kotlin-api-coverage.json` maps 737 of the 873 members the Swift manifest lists to a Kotlin symbol and marks the other 136 excluded for the reason Swift gives; none is pending.

## Validation

`.github/workflows/release-android.yml` builds and checks the package in the development image (`.devcontainer/Dockerfile`) on `ubuntu-24.04`, before the approval. It checks that the engine pin in `platforms/android/embedpdf/gradle.properties` matches `android-engine-hash.sh` for the tree, and asks the GitHub Packages registry that no library is already published at `0.0.0-android.1`. It links the engine against the `android-arm64` and `android-x64` fork slices built earlier in the same run, after checking both are their target at the `runtime-src` gitlink. Then:

- `build-aar.sh test` builds both ABIs, checks 16 KB `LOAD` alignment on every `.so` and `zipalign -c -P 16` on the bindings test APK, runs `apiCheck` on the four API modules and `:models:checkNoCompose`, and runs the JVM unit tests: `testDebugUnitTest` for `bindings`, `embedpdf`, `javascript`, `models` and `compose` (the Compose tests under Robolectric), and `:smoke:test`.
- `scripts/check-api-coverage.py --platform kotlin` and `apiCheck` again.
- `android-consumer.sh` stages the five artifacts at `0.0.0-android.1` in a local Maven repository, checks that exactly those five publish, each at one version, with every POM dependency versioned, then builds the minified release demo from them and checks uncompressed engine storage, `zipalign -c -P 16 4`, and R8's `usage.txt` and `mapping.txt` for removed or renamed `uniffi.*` and `com.sun.jna.*` classes.
- The unit tests of `package-maven-zip.py` and `publish-staged.sh`, then `package-maven-zip.py` writes the zip.
- The minified demo is built once more from the zip, checked with `sha256sum -c` and unzipped, with `-Pembedpdf.mavenRepository` and no Maven Local.

The `packages` job uploads the same staged files the consumer check used, not a second build.

No emulator or device test runs in CI. `./gradlew check` isn't run either, so Android lint isn't part of the release. The signature route tests (`SignatureRoutesTest`) skip themselves when `node` or a built `packages/core/signature/dist` is missing, and the build stage doesn't build that `dist`, so they skip; the run's logs have the test counts.

## Known gaps

The instrumented tests (`DeviceViewerTest`, `DeviceKeyStoreTest`, `DeviceSandboxTest`, `DeviceStageReaderTest`, `DeviceSearchHighlightTest`) last ran on 2026-11-26, by hand, on one `Pixel_4` emulator with the arm64 16 KB page image `android-37.1` and WebView 157.0.8103.50. That run predates [`96d925b73`](https://github.com/MFB-Technologies-Inc/embed-pdf-viewer/commit/96d925b73), so it was against engine `android-engine-8dae75e9c47886ab`, not the `9d9ec62d682771fa` this release ships. Nothing has run on physical hardware, and the `x86_64` engine has never been executed. Three paths are covered only by that emulator run:

- The JavaScript sandbox. CI's `javascript` tests run under Robolectric, which has no WebView, so they cover the unavailable path and the `ScriptEngine` contract through a fake isolate; `DeviceSandboxTest` is the only test that evaluates a script in the real sandbox. On that run, pressing `btn-chain` in `action_buttons_form.pdf` left the log field at "B" where the TypeScript plugin expects "AB": the Rust actions plugin's second script doesn't see the first one's write. It is not fixed.
- The first ink stroke. Under Robolectric the first stroke after the ink tool turns on doesn't commit, so the CI test `StageReaderTest` draws until ink lands and can't catch a first-stroke regression. On the emulator the first stroke created the annotation (`DeviceStageReaderTest`).
- The Keystore signer. CI's `AndroidKeyStoreSignerTest` signs with a key from `KeyPairGenerator.getInstance("EC")`, not the Keystore. On the emulator, EC P-256 Keystore keys signed and keys requiring user authentication failed with `permission-denied` (`UserNotAuthenticated`), but a key requiring a biometric per use couldn't be generated, since the emulator had no biometric enrolled, and no test answers a biometric or credential prompt.

A dispatcher that resumes inline (`Dispatchers.Unconfined`, or Compose's default `UnconfinedTestDispatcher` in instrumented tests) crashes the process when it calls into the viewer, because JNA detaches a native thread that is still running a callback. The facade's own calls run on `Dispatchers.Default`; an app's instrumented tests over these views need a `StandardTestDispatcher` as the effect context.

Printing is not implemented: `Documents.print`, `prepare_print`, `get_print_quality` and `can_print` are excluded because the native host has no `HostPrinter`, as on Apple. PDF JavaScript needs API 26 and a WebView where `JavaScriptSandbox.isSupported()` is true, and reports itself unavailable elsewhere. The demo app has no UI tests.
